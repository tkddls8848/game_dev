# PoC 공장 — 폴더 규약과 작업 순서

> 작성 2026-09-27. 여러 컨셉·여러 장르·같은 장르의 여러 연출을 **PoC 수준으로 많이** 찍어 내기 위한 규약.
> 공통 개발 규율은 뿌리 `CLAUDE.md`, 장르별 계획은 `docs/PLAN_*.md`.

> **필수 품질 기준:** [CLAUDE.md의 '게임은 감각까지 구현한다'](../CLAUDE.md)를 따른다. 헤드리스 검증은 규칙 구현의 증거다. 플레이 가능한 게임 PoC를 요청받았다면 승인 시안을 기준으로 에셋·조명·이펙트·움직임·조작 피드백까지 구현해야 하며, 빌드 성공만으로 완료 처리할 수 없다.

> **그래픽·사운드·조작감에는 타협하지 않는다.** 이 문서의 빠른 제작·다작·최소 슬라이스 원칙은 콘텐츠와 기능의 범위를 작게 잡으라는 뜻이지, 플레이어가 경험하는 품질을 낮추라는 뜻이 아니다. 승인 시안과 요구 품질에 미달하면 게임 PoC는 미완료다. 범위 조정이 필요해도 사용자 지정 범위를 임의로 줄이지 않는다. 상세 기준은 CLAUDE.md의 '최우선 원칙'을 따른다.

## 1. 이 규약이 푸는 문제

다작에서 시간을 먹는 것은 게임 설계가 아니라 **되풀이되는 준비**다. 셋이 특히 비싸다.

| 비용 | 실제 크기 | 이 규약의 대응 |
|---|---|---|
| **Unity 프로젝트 하나당 `Library/`** | 17,000+ 파일 · GB 단위. 생성에 분 단위 | **PoC는 Unity 없이 시작한다.** 살아남은 것만 `unity/`를 갖는다 |
| **방식을 다시 세우기** | asmdef 3분할 · 테스트 프로젝트 · 검사기 · 팔레트 · 로컬라이제이션 | `kit/`과 뿌리 `CLAUDE.md`가 한 벌로 정해 둔다 |
| **판정이 느림** | Unity를 띄워야 확인되면 하루에 PoC 하나 | 헤드리스 테스트 **0.3초**. 하루에 스무 개를 본다 |

> **핵심 한 줄: PoC는 헤드리스로 태어나고, 재미가 확인된 것만 Unity를 얻는다.**
> 이 순서를 뒤집으면 `Library/`가 디스크를 먹고 판정이 느려져 다작 자체가 멈춘다.

## 2. 폴더

```
orca/game/
  CLAUDE.md                   공통 규율 (모든 PoC가 따른다)
  README.md                   저장소 지도
  .env                        API 키 (gitignore) · .env.example 이 목록
  kit/
    tools/                    범용 도구 (--game 으로 대상을 받는다)
  games/
    <슬러그>/                 PoC 하나 = 폴더 하나
  docs/
    POC_FACTORY.md            이 문서
    PLAN_*.md                 장르별 계획 (착수 전 조사·판정)
  AssetDownloads/             내려받은 원본 (gitignore) · 게임들이 공용
```

**`.env`는 위 저장소 최상위 한 개만 사용한다.** 게임·도구 폴더에 복제하거나 `.env.local` 등 실행용 변형 파일을 만들지 않는다. 실행 위치가 달라도 저장소 루트의 파일을 읽도록 경로를 계산한다. 비밀값 없는 루트 `.env.example`은 변수 목록을 설명하는 템플릿이다. 실제 `.env`는 Git·Unity 에셋·빌드에 포함하지 않는다.

### PoC 하나의 안

**최소(헤드리스 단계) — 여기서 대부분이 죽는다:**

```
games/<슬러그>/
  README.md              ★ 필수. 한 장 (§4)
  src/                   순수 C#. UnityEngine 참조 금지
  data/                  JSON
  tests/
    <슬러그>.Tests.csproj  NUnit. src/ 와 data/ 를 직접 가리킨다
```

**졸업 뒤(Unity 셸이 붙는다):**

```
games/<슬러그>/
  README.md · CLAUDE.md  이 게임의 사실
  unity/                 Unity 프로젝트
  tests/                 위 테스트 프로젝트 (이제 unity/Assets 를 가리킨다)
  tools/                 이 게임 전용 생성기
  docs/                  이 게임 전용 문서
```

> **`mystery-blackwood`는 이 순서를 거꾸로 밟았다.** Unity로 먼저 시작해서 순수 로직이
> `unity/Assets/Scripts/` 안에 있다(asmdef가 요구한다). 잘 돌고 검증돼 있으므로 건드리지 않는다.
> **새 PoC는 `src/`로 시작한다.**

### 슬러그 이름

`<장르>-<컨셉>` 꼴. **번호를 붙이지 않는다** — 순서가 바뀌면 전부 이름을 고쳐야 한다.

```
games/mystery-blackwood/      추리 · 블랙우드 저택
games/deck-rewind/            덱빌더 · 되감기
games/deck-rewind-noir/       같은 로직, 누아르 연출          ← 연출 변형
games/farm-erosion/           파밍 · 땅이 줄어드는 세계
```

### 같은 장르의 여러 연출

**로직을 복사하지 않는다.** 로직 PoC를 라이브러리로 두고 연출별 PoC가 그것을 참조한다.

```
games/deck-rewind/        ← 로직 + 데이터. 라이브러리 역할. README에 "로직 전용"이라 적는다
games/deck-rewind-noir/   ← ../deck-rewind 참조 + 자기 연출
games/deck-rewind-paper/  ← 같은 로직, 다른 연출
```

csproj의 `ProjectReference`로 잇는다. **복사하면 반드시 갈라지고, 갈라지면 어느 쪽이
진짜인지 매번 판단해야 한다** — 이 저장소가 Godot 이식에서 한 번 배운 것이다.

## 3. 작업 순서

```
아이디어
   │
   ├─ 0. docs/PLAN_<장르>.md 를 쓴다 (착수 전 조사·판정·리스크·확인 못한 것)
   │        └─ 여기서 접는 것이 가장 싸다
   │
   ├─ 1. games/<슬러그>/ 를 만든다 — src/ + data/ + tests/ + README.md
   │        완료 조건: 같은 씨드로 두 번 돌려 같은 결과 (헤드리스)
   │
   ├─ 2. 수직 슬라이스. 규칙 최소 단위만 (카드 5장 · 작물 3종 수준)
   │        ★ 사람이 판정한다. 여기가 분기점이다
   │        재미없으면 → 접는다. README에 왜 접었는지 적고 남긴다
   │
   ├─ 3. 검사기를 채운다 (§5). Phase는 검사기 통과로 닫는다
   │
   └─ 4. 졸업: unity/ 를 만든다. 여기서부터 비싸진다
```

**2번에서 접는 것을 실패로 취급하지 않는다.** 그게 이 공장의 산출물이다 —
스무 개를 싸게 죽여서 하나를 찾는 구조다. 접은 PoC는 **지우지 말고 README에 사인을 적어 남긴다.**
같은 아이디어가 반년 뒤에 다시 올라오고, 그때 왜 접었는지 알아야 한다.

### 새 PoC 시작하기

**`kit/templates/poc/`를 복사하고 `__SLUG__`를 바꾼다.**
안에 `PoC.csproj.template` · `src/` · `tests/` · `data/` · `presentation/` · `README.md` · `CREDITS.md`가 있다.

> 템플릿은 **두 번째 헤드리스 PoC를 만들 때** 만들었다. 하나뿐일 때 만들었다면
> 그 하나의 모양을 일반화한 것일 뿐이고, 대개 틀렸을 것이다.

## 4. README.md — PoC마다 필수, 한 장

사람과 에이전트가 **폴더를 열지 않고** 상태를 알 수 있어야 한다. 항목은 여섯 개.

```markdown
# <슬러그>

**한 줄**: 무엇을 하는 게임인가
**장르 표기**: 스토어에 낼 때의 태그 (퍼즐로 분류되면 위험하다 — PLAN 문서 참고)
**상태**: 구상 / 헤드리스 / 슬라이스 / Unity / 접음
**판정**: 마지막으로 사람이 본 결과. 날짜와 함께
**검증**: 돌리는 명령 한 줄과 현재 통과 수
**다음**: 하나만
```

`상태: 접음`이면 **왜 접었는지를 판정 칸에 반드시 적는다.**

## 5. 검사기 — Phase를 닫는 것

공통 원칙 7번: 검사기 통과로 기술적 동작을 검증한다. **게임 PoC의 완료에는 감각 구현과 시안 비교 검증도 필요하다.**
기계의 고장 검증, 실제 빌드의 연출·피드백 검증, 사람의 재미·만족 판정을 구별한다.

### 플레이 가능한 게임 PoC의 완료 증거

1. 규칙·입력·성공·실패 흐름이 실제 빌드에서 동작한다.
2. 승인 시안과 실제 화면을 동일하거나 대응되는 카메라·플레이 상태로 비교한다. 구도·밀도·팔레트·재질·조명·배경·UI가 크게 다르면 완료 전 수정한다.
3. 에셋을 이용한 환경 연출과 행동 피드백을 실제 플레이 녹화 또는 연속 캡처로 검증한다. 단순히 수치가 바뀌는 것으로 성장·수확·붕괴·승인 등의 연출을 대신하지 않는다.
4. README에 기술 검증, 감각 구현·시안 비교 결과, 남은 차이, 사람 판정을 각각 기록한다. 기본 도형만 있는 결과물은 규칙 검증용 프로토타입으로 표기한다.

| 기계가 판정한다 (고장) | 사람만 판정한다 (재미) |
|---|---|
| 참조 무결성 · 씨드 재현성 | 손맛 · 긴장 · 페이싱 |
| 이길 수 있는가 · 지배 전략이 없는가 | 연출이 무겁게 느껴지는가 |
| 쓸모없는 선택지가 없는가 | 두 루프가 붙어 있다고 느끼는가 |
| 타이밍·경제가 발산하지 않는가 | 목소리가 서로 다른 사람으로 들리는가 |

`mystery-blackwood`에서 이 구별이 값을 한 실제 사례:
음성 190개를 뽑기 **전에** 타이밍 시뮬레이션이 여유 부족을 잡아 냈다. 뽑고 나서 알았다면 전부 버렸다.
반대로 "연기가 괜찮은가"는 지금도 기계가 못 본다 — 그건 사람 몫으로 남겨 두고 그렇게 적었다.

각 장르에서 기계가 어디까지 볼 수 있는지는 `docs/PLAN_*.md` §검증에 장르별로 적어 두었다.
**덱빌더가 가장 넓고 파밍이 가장 좁다.** 그게 1인 개발에서 장르를 고르는 실제 근거다.

## 6. 하지 말 것

* **Unity 프로젝트를 PoC마다 만들기.** `Library/`가 GB 단위다. §1
* **로직을 복사해서 연출 변형 만들기.** 참조로 잇는다. §2
* **접은 PoC를 지우기.** 이유를 잃는다. README에 사인을 적고 남긴다. §3
* **`UnityEngine.Random`이나 float 누적.** 헤드리스 재현이 깨지고 검증 전체가 무의미해진다
* **검사기 통과를 재미로 착각하기.** §5
* **하나뿐일 때 템플릿 만들기.** §3

**재미 판정은 아직 아무도 하지 않았다.**
계획서는 다섯 장르 모두 [`PLAN_GENRES.md`](PLAN_GENRES.md) 한 문서에 있다
(§1 파밍 · §2 덱빌더 · §3 결합 · §4 전술 · §5 턴제 전략).

### 검사기가 실제로 설계를 고쳤다

§5가 "고장만 잡는다"고 적었는데, 첫 수확에서 셋이 걸렸다. 이게 이 방식을 고른 이유의 증거다.

* **`deck-rewind`** — "크게 맞으면 되감는다" 정책이 승률 34%로 **아예 안 쓰는 57%보다 나빴다**
  (적의 기억이 전투 내내 남기 때문). "죽었을 때만"으로 고쳐 69%
* **`deck-openhand`** — 가림막이 오히려 29%p 손해인 **벌**이어서 조건을 다시 짰다
* **`hybrid-*`의 `SeasonFeasibility`** — 두 번 실패했다: 봄에 방어 작물이 없어 0%,
  씨앗을 봄에 다 써 밀을 못 심어 수확 카드 사용률 0%. **"밭이 덱을 만든다"가 데이터에서 깨져 있었다**

반대로 기계가 판정하지 못한 것도 정직하게 남았다 — `farm-rewind-year`는 탐욕 정책에서
완전한 지식이 무지보다 141코인 **덜** 남겨서 "학습이 흔적을 이기는가"를 판정할 수 없었고,
그 검사기는 수치만 출력하고 부호를 단정하지 않는다.
