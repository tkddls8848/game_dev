# deck-openhand

**한 줄**: 적의 다음 다섯 수가 늘 보인다. 아무것도 숨기지 않으므로 문제는 "무엇이 올까"가 아니라 "어느 순서로 받을까"이고, 카드로 그 순서를 지우거나 뒤집는다.

**장르 표기**: 로그라이크 덱빌더 (Roguelike Deckbuilder · Card Battler · Strategy).
**⚠️ 퍼즐로 분류될 위험이 이 PoC의 가장 큰 위험이다** — 아래 "퍼즐 위험" 절을 먼저 읽을 것.
`docs/PLAN_GENRES.md §2` §3의 후보 "공개 덱"을 그대로 구현한 것이다.

**상태**: 헤드리스 (수직 슬라이스). Unity 프로젝트 없음 — `docs/POC_FACTORY.md` §1대로 헤드리스로 태어났다.

**판정**:
*기계가 본 것 (2026-09-27)* — 검사기 40개 전부 통과. 고장은 없다.
지배 전략 없음(단일 카드 덱 최고 승률 4%) · 사장 카드 없음(최저 채택률 11%) ·
준최적 승률 72%, 무작위 0% · 씨드 재현 완전 · 예고된 다섯 수가 실제로 오는 순서와 일치한다.
**규칙이 값을 한다는 증거**: 순서를 읽는 준최적 **68%** vs 같은 정책이 순서를 무시할 때 **43%**.
25%p 차이가 "보이는 것"이 장식이 아니라는 뜻이다 (`OpenHandRuleTests.순서를_읽는_쪽이_읽지_않는_쪽보다_낫다`).
80판에서 가림막 84회 · 역순 190회 — 순서를 건드리는 카드가 실제로 쓰인다.
*사람이 봐야 하는 것* — **재미는 미확인이다.** 아직 아무도 손으로 플레이하지 않았다.
특히 이 둘은 기계가 못 본다:
(1) 다 보이는데도 **긴장**이 있는가. 아니면 계산 숙제인가
(2) 순서를 맞추는 것이 **읽는 재미**인가 아니면 **정해진 답 찾기**인가 — 후자면 퍼즐이다.
검사기가 통과한 것은 **고장이 없다**는 뜻일 뿐이다.

**검증**:
```bash
C:/Users/PSI/.dotnet/dotnet.exe test games/deck-openhand/tests/deck-openhand.Tests.csproj
# 40/40 통과 · 1초
```

**다음**: 사람이 한 판 해 보고 위 (2)를 판정한다 — 읽는 재미인가 정해진 답 찾기인가.
그 답이 "답 찾기"면 접는다. 여기서 접는 것이 가장 싸다.

## 퍼즐 위험 — 이 PoC의 실제 리스크

`docs/PLAN_GENRES.md §2` §3이 이 후보에 붙인 위험은 하나다:
**"퍼즐(성공률 0.34%)로 분류될 위험"**. 덱빌더가 5.1%인데 퍼즐은 그 **15분의 1**이다.
태그 하나가 아니라 게임이 어떻게 읽히는지의 문제이므로 정직하게 적는다.

**퍼즐 쪽으로 미는 것 (이 PoC가 실제로 한 것):**
* 적의 행동에 난수가 **전혀** 없다 (`OpenHandRuleTests.적의_행동에는_난수가_없다`가 이걸 강제한다)
* 다음 다섯 수가 늘 보인다 — 숨긴 정보가 없다
* `대비`는 다음 수의 값을 **정확히** 막는다. 계산이 딱 맞는다

**덱빌더 쪽에 남겨 둔 것:**
* **손패는 무작위다.** 난수가 닿는 곳이 하나 남아 있고 그게 카드를 뽑는 순서다 —
  같은 상황에 매번 다른 수단이 손에 온다. 정해진 해가 없다
* 적의 순서가 6~7수라 **보이는 창(5)보다 길다.** 끝까지 보이지 않는다
  (`DataValidatorTests.적의_패턴이_보이는_창보다_길다`가 이걸 강제한다)
* 회차마다 덱이 바뀐다 (보상)

**아직 판정하지 못한 것:** 위 둘의 균형이 사람에게 어떻게 느껴지는가.
기계는 "정해진 해가 없다"는 것만 확인할 수 있고, **"퍼즐처럼 느껴지는가"는 못 본다.**
그 판정이 이 PoC의 분기점이다.

## 규칙 — 순서를 다루는 네 장

보이는 것이 정보일 뿐이면 퍼즐도 덱빌더도 아니다. **순서를 건드릴 수단**이 있어야 규칙이 된다.

| 카드 | 코스트 | 하는 일 | 순서를 |
|---|---|---|---|
| `대비` | 1 | 다음 수가 공격이면 **그 값만큼** + 2 방어 | 읽는다 |
| `메아리` | 1 | 보이는 다섯 수 중 **공격 하나마다** 피해 3 | 읽는다 |
| `역순` | 1 | 다음 두 수의 **자리를 바꾼다** — 큰 공격을 뒤로 민다 | 바꾼다 |
| `가림막` | 2 | 다음 한 수를 **지운다** — 일어나지 않은 것으로 친다 | 지운다 |

`DataValidatorTests.순서를_건드리는_카드가_하나_이상_있다`가 이 중 둘 이상을 강제한다.
하나도 없으면 "보인다"는 것이 정보일 뿐 퍼즐이 아니게 되기 때문이다.

측정으로 알아낸 것: `가림막`의 값을 **"가장 큰 공격이 바로 다음일 때만"**으로,
그리고 **이미 사 둔 방어가 덮는 몫을 뺀** 값으로 재게 하기 전까지,
가림막은 받으면 승률이 29%p 떨어지는 **벌**이었다 (`DeadCardCheckerTests.유독_못한_보상이_없다`가 잡았다).
카드가 나쁜 것이 아니라 **아무 때나 쓰면 낭비**였던 것이고, 그게 이 규칙의 성격이다.

## 구조

```
src/            순수 C#. using UnityEngine 없음
  Rng.cs          씨드 고정 난수. 닿는 곳은 카드를 뽑는 순서 하나뿐이다
  Data.cs         JSON 스키마 + 로더
  Battle.cs       전투 상태 기계 + 예정 행동 대기열(지우기/자리바꿈)
  Agents.cs       무작위 · 준최적(탐욕) · 순서를 안 보는 대조군
  RunEngine.cs    회차 진행 + 몬테카를로
  Localization.cs 한국어 원문 + 영어 덮어쓰기
data/           cards.json(11종) · enemies.json(3종) · runs/run_01.json · balance.json
tests/          NUnit. 검사기 여섯 + 규칙 테스트
presentation/   palette.json · index.html · scene.json(생성물) · assets/
```

`src/`는 **같은 장르의 다른 연출**이 아니라 **다른 규칙**이다 (`games/deck-rewind`는 되감기).
`docs/POC_FACTORY.md` §2가 금지하는 것은 연출 변형을 위해 로직을 복사하는 것이고,
규칙이 다르면 로직도 다르다. **이 PoC의 연출 변형을 만들 때는 복사하지 말고
`ProjectReference`로 이 폴더를 가리킬 것.**

## 검사기 — Phase를 닫는 것 (`docs/PLAN_GENRES.md §2` §5)

| 검사기 | 파일 | 재는 것 | 지금 값 |
|---|---|---|---|
| `DataValidator` | `DataValidatorTests.cs` | 참조 무결성 · 순서 카드 존재 · 패턴 > 창 | 통과 |
| `SeedDeterminism` | `SeedDeterminismTests.cs` | 같은 씨드 = 같은 기록. 난수가 손패에만 닿는가 | 통과 |
| `RunSolvability` | `RunSolvabilityTests.cs` | 준최적으로 이길 수 있는가 | 16/30 씨드 |
| `DominanceChecker` | `DominanceCheckerTests.cs` | 단일 카드 덱 승률 ≤ 55% | 최고 4% |
| `DeadCardChecker` | `DeadCardCheckerTests.cs` | 채택률 ≥ 5% · 벌이 되는 보상 없음 | 최저 11% |
| `WinRateBand` | `WinRateBandTests.cs` | 무작위 0~5% · 준최적 40~80% | 0% / 72% |
| (규칙) | `OpenHandRuleTests.cs` | 예고가 진짜인가 · 순서가 값을 하는가 | 통과 |
| (원칙 6) | `LocalizationTests.cs` | 표가 없어도 한국어가 나오는가 · 언어가 굳지 않는가 | 통과 |

한계값은 전부 `data/balance.json`에 있다. 테스트에 매직 넘버를 두지 않는다 —
판정선이 숨으면 밸런스를 고칠 때 무엇이 움직였는지 알 수 없다.

> **구간의 목표값 자체는 확인하지 못한 것이다** (`docs/PLAN_GENRES.md §2` §10).
> 기존 성공작의 실제 승률 분포를 모른다. `balance.json`의 구간은 "옳은 값"이 아니라
> **이 PoC가 지금 어디 있는지를 고정하는 값**이다.

## 연출 — 목판화 타로

크림색 종이가 **바탕**이고 글자가 검다 (`deck-rewind`와 정반대다) · 검은 해칭으로 명암 ·
붉은 강조 **하나**만 (활판 인쇄가 두 번째 판을 쓰던 자리) · 세리프 글꼴 하나(EB Garamond) ·
스몰캡스. 적의 초상은 Rider-Waite 타로(1909, 퍼블릭 도메인)이고,
채도를 걷어 세피아를 얹어 판화 쪽으로 민 것은 `palette.json`의 `grade.art*` 값 셋이다 —
**원본 파일은 건드리지 않았다.** 정해진 운명을 읽는 감각을 만들려는 것이다.

목업 보기 (저장소 뿌리에서):
```bash
python -m http.server 8000 --directory games/deck-openhand
# http://localhost:8000/presentation/
```
`file://`로 열면 브라우저가 `fetch`를 막는다 — 목업이 `data/`의 **실제 JSON**을 읽기 때문이다.
전투 장면(`presentation/scene.json`)도 손으로 쓴 것이 아니라
`tests/SceneExportTests.cs`가 실제 시뮬레이션에서 굽는다.
특히 **예고된 다섯 수**는 반드시 생성물이어야 한다 — 손으로 적으면
"늘 보인다"는 규칙 자체가 목업에서 거짓말이 된다.
