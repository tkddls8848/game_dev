# deck-attrition

**한 줄**: 강한 카드에는 남은 인쇄 횟수가 있고, 그 횟수는 한 판이 아니라 **회차 전체에서** 줄어든다. 다 쓰면 녹여 버리고 회차가 끝날 때까지 돌아오지 않는다. 그래서 매 턴의 질문이 "무엇을 낼까"가 아니라 **"지금 쓸까 아껴 둘까"**가 된다.

**장르 표기**: 로그라이크 덱빌더 (Roguelike Deckbuilder · Card Battler · Turn-Based Strategy).
퍼즐 태그는 붙이지 않는다 — 손패가 무작위이고 회차마다 보상이 달라 정해진 해가 없다.
`docs/PLAN_GENRES.md §2` §3의 **세 번째 후보 "소모되는 카드"**를 그대로 구현한 것이다.

**상태**: 헤드리스 (수직 슬라이스). Unity 프로젝트 없음 — `docs/POC_FACTORY.md` §1대로 헤드리스로 태어났다.

**판정**:

*기계가 본 것 (2026-09-27)* — 검사기 47개 전부 통과. 고장은 없다.

**핵심은 이것 하나다.** 계획서 §3이 이 후보에 붙인 위험은 *"아끼기만 하는 지루한 최적해가 생길 수 있다"*였다.
같은 탐욕 코드에 **정책 하나만 갈아 끼워** 300회차씩 돌린 결과:

| 정책 | 승률 | 보스 앞에 섰을 때 |
|---|---|---|
| **끝까지 아낀다** (보스에서만 꺼낸다) | **25%** | 남은 횟수 12.13 · 체력 10.1 · 그런데 **보스를 51%만 본다** |
| **적절히 쓴다** | **64%** | 남은 횟수 6.22 · 체력 46.1 · 보스 도달 100% |
| **즉시 쓴다** (손에 오면 찍는다) | **24%** | 남은 횟수 1.45 · 체력 65.3 · 보스 도달 100% |

아끼는 쪽이 **39%p**, 즉시 쓰는 쪽이 **40%p** 진다. 위험은 데이터에서 살아나지 않았다.
표의 오른쪽 칸이 이유다 — **아끼는 값은 활자가 아니라 체력으로 낸다.** 끝까지 아끼면
보스 앞에 열두 번의 인쇄를 들고 서지만 체력이 10이라 대개 그 앞에 도달하지도 못하고,
즉시 쓰면 체력 65로 도착하지만 손에 남은 것이 없어 마감(14판) 안에 압판을 못 찍는다.

그 밖에:
지배 전략 없음(기본 활자에 한 카드를 7장 쌓은 덱의 최고 승률 3%) ·
사장 카드 없음(최저 채택률 8%) · 무작위 회차 0% vs 준최적 64% ·
씨드 재현 완전(마모 상태까지) · **이긴 회차의 100%에서 활자가 실제로 녹는다**(회차당 3.84종).

*사람이 봐야 하는 것* — **재미는 미확인이다.** 아직 아무도 손으로 플레이하지 않았다.
기계가 본 것은 **"아끼는 것이 최적이 아니다"**까지다. 아래 둘은 기계가 못 본다:

1. **아까움이 긴장인가 잡일인가.** 강한 카드를 손에 들고 안 내는 턴이 *참는 맛*인지
   *그냥 답답한 것*인지는 사람만 안다. `games/hybrid-siege-seasons`가 같은 질문을 해 단위로
   남겨 두었고, 그것도 아직 답이 없다
2. **녹는 순간이 아픈가.** 다 쓴 활자가 덱에서 사라지는 것이 *사건*처럼 느껴져야 한다.
   숫자로는 "자원이 줄었다"일 뿐이다

검사기가 통과한 것은 **고장이 없다**는 뜻일 뿐이다.

**검증**:
```bash
C:/Users/PSI/.dotnet/dotnet.exe test games/deck-attrition/tests/deck-attrition.Tests.csproj
# 47/47 통과 · 약 2초
```

**다음**: 사람이 한 회차를 손으로 플레이해 위 1번을 판정한다 — 아끼는 것이 긴장인가 잡일인가.
잡일이면 접는다. 여기서 접는 것이 가장 싸다.

## 규칙 — 활자는 회차 전체에서 닳는다

`games/deck-rewind`·`games/deck-openhand`와 **규칙이 다르다.** 연출 변형이 아니므로 로직도 따로 있다.

| 되돌아오는 것 | 되돌아오지 않는 것 |
|---|---|
| 손패 · 덱 · 버림 · 기력 (전투마다) | **남은 인쇄 횟수** — 회차 하나에 3회 / 2회 / 1회 |
| 적의 체력 · 방어 (전투마다) | **선명도** — 찍을수록 뭉개지고 효과가 그만큼 약해진다 |
| — | **체력** — 전투 사이에 한 번도 차지 않는다 (`healAfterBattle: 0`) |
| — | **녹은 활자** — 덱·손·버림 어디에 있든 전부 사라지고 보상으로도 안 돌아온다 |

**횟수는 카드 장 수가 아니라 활자 하나에 붙어 있다.** 덱에 같은 카드가 두 장 있어도
물리적인 활자는 하나이므로, 다 닳으면 두 장이 한꺼번에 사라진다.
보상도 장을 더하는 것이 아니라 **활자를 다시 주조한다**(이미 있으면 남은 횟수 +1).

**선명도가 왜 필요한가.** 닳는 것이 있다/없다 둘뿐이면 "마지막에 몰아 쓴다"가 늘 옳고,
계획서가 경고한 그 지루한 최적해가 그대로 생긴다. 선명도가 있으면 **첫 인쇄가 가장 선명하다**는
사실이 생겨서, 쓰는 순간을 고르는 것 자체에 값이 붙는다.

측정값:
* `대형 목활자`(피해 20, 마모 20%): **20 → 16 → 12** 로 찍히고 세 번째 뒤에 녹는다
* 백분율 정수 + **나머지 누적**: 선명도 80%로 7을 20번 찍은 합이 정확히 112 (설계값과 일치)
* 선명도 바닥 40% — 그 아래로는 안 내려간다. "남았는데 아무 일도 안 일어나는 카드"는 고장으로 읽힌다
* 마감 14판. **기본 활자만 14장으로는 가득 찬 체력에서도 보스를 8%밖에 못 잡는다** —
  아껴 둔 활자를 쓸 데가 있어야 아끼는 것이 결정이 된다

**적의 다음 한 수는 보인다.** 숨기지 않는 이유는 규칙 때문이다 — 무엇이 오는지 알아야
"지금 쓸까"가 도박이 아니라 결정이 된다. (`deck-rewind`는 숨기고, `deck-openhand`는 다섯 수를 보여 준다.)

## `hybrid-siege-seasons`와 무엇이 다른가

그 PoC가 같은 손잡이(`durability`)를 **해 단위**로 썼고 파밍 층이 붙어 있었다.
여기는 **회차 단위**이고 덱빌더 단독이다 — 밭도, 계절도, 카드 생성기도 없다.
**목적이 "이 규칙 하나만으로 덱빌더가 성립하는가"**이므로 다른 것을 섞지 않았다.

| | hybrid-siege-seasons | **deck-attrition** |
|---|---|---|
| 마모의 시간축 | 해 (여러 회차) | **회차 하나** (전투 4개) |
| 카드의 출처 | 밭에서 수확한다 | 시작 덱 + 보상 |
| 닳는 방식 | 남은 횟수만 | 남은 횟수 **+ 선명도**(효과가 같이 약해진다) |
| 아끼는 값의 대가 | 다음 해 | **체력** — 전투 사이에 안 찬다 |
| 핵 검사기 | `SeasonFeasibility` (두 루프가 붙어 있는가) | **`HoardingIsNotOptimal`** (아끼기가 최적이 아닌가) |

## 구조

```
src/            순수 C#. using UnityEngine 없음
  Rng.cs          씨드 고정 난수 (System.Random + 데이터의 씨드)
  Data.cs         JSON 스키마 + 로더
  TypeCase.cs     ★ 활자 상자. 회차 단위 마모(남은 횟수 · 선명도 · 나머지 누적)가 여기 산다
  Battle.cs       전투 상태 기계. 마모 상태를 갖지 않고 상자를 빌려 쓴다
  Agents.cs       무작위 + 식자공(정책 셋: 아낌 / 적절히 / 즉시)
  RunEngine.cs    회차 진행 + 보상(주조) + 몬테카를로
  Localization.cs 한국어 원문 + 영어 덮어쓰기
data/           cards.json(10종 · 닳는 것 5종) · enemies.json(3종) · runs/run_01.json · balance.json
tests/          NUnit 47개. 검사기 일곱 + 규칙 테스트 + 장면 생성
presentation/   palette.json · index.html · scene.json(생성물) · assets/
```

**정책 셋은 같은 탐욕 코드를 쓴다.** 갈라지는 자리는 `TypesetterAgent.AllowsConsumable` 하나뿐이다.
정책마다 다른 판단 규칙을 쓰면 승률 차이가 규칙 때문인지 정책 때문인지 말할 수 없고,
그러면 핵 검사기가 아무것도 증명하지 못한다.

### 측정이 설계를 고친 자리

밸런스를 감으로 맞추지 않았다는 증거로 두 개만 남긴다.

* **처음 데이터에서는 "즉시 쓴다"가 60%로 압승했다.** 활자 횟수가 회차 길이에 비해 넉넉해서
  먼저 쓰는 쪽이 체력을 아끼고 그 이득이 복리로 쌓였다. 횟수를 줄이고, 전투 사이 회복을 **0**으로
  내리고, 보스를 마감 안에 기본 활자로는 못 잡게 만든 뒤에야 안쪽 최적해가 생겼다
* **한때 "적절히 쓴다"가 체력 19.8로 보스 앞에 섰다.** 탐욕 점수에 닳는 활자 벌점을 -300으로
  크게 주는 바람에, 정책이 허락한 카드를 점수가 다시 막아 **회복 활자가 통째로 죽어** 있었다.
  벌점을 -60으로 낮추자 체력 46.1이 됐다 (승률 11% → 64%). 두 번 거르면 안 된다

## 연출 — 납 활자 · 인쇄소

활판 인쇄. 검정과 납회색 두 색에 **주홍 한 점**, 잉크가 번진 자리, 글자마다 미세하게 다른 농도.
**활자가 닳는 것이 카드가 닳는 것과 같은 그림이다** — 많이 쓴 활자는 뭉개져 찍힌다.

그래서 목업은 **카드에 남은 횟수를 숫자로 적지 않는다.** 잉크의 농도·번짐·자간이 곧 남은 횟수다.
손에 든 것은 아직 **금속**(납회색 활자)으로, 낸 것은 종이 위의 **찍힘**(크림색 인쇄)으로 그린다 —
낸다 = 찍는다 = 닳는다가 한 화면에서 읽힌다.
색·크기·번짐값·눌린 자국은 전부 `presentation/palette.json`에 있고 HTML에는 박혀 있지 않다.

목업 보기 (저장소 뿌리에서):
```bash
python -m http.server 8000 --directory games/deck-attrition
# http://localhost:8000/presentation/
```
`file://`로 열면 브라우저가 `fetch`를 막는다 — 목업이 `data/`의 **실제 JSON**을 읽기 때문이다.
회차 장면(`presentation/scene.json`)도 손으로 쓴 것이 아니라 `tests/SceneExportTests.cs`가
**이기면서 활자가 녹는 씨드를 훑어 골라** 실제 시뮬레이션에서 굽는다. 데이터를 고치면 목업이 같이 바뀐다.
